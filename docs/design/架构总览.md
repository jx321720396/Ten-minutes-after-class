# 架构总览

> 状态：草案 ｜ 维护者：程序 ｜ 最后更新：2026-10-04
> 规格依据：`../gdd/core-gameplay-v3.1.md` §3（时间）、§4（三层 + 观察层）、§6–§7（数值与传导）、§10（规则）

## 1. 模拟内核 ↔ 表现层

本作是**数据驱动模拟**：内核每 tick 计算完成后再通知表现层，表现层不参与数值计算。

```
       ┌──────────────────────── SimulationCore（无 UI 依赖，可无头运行）────────────────────────┐
       │  TimeSystem ──tick──► RuleScheduler ──► Behaviors(§10) ──► Relations(A/H/T) / Stress     │
       │        ▲                    │                                   │                       │
       │        │                    └──► 涓流结算：传导/共同学习/独处（每天 2 次，§7.2）           │
       │   TermState（天/段/相位）                   │                                           │
       │                                             └──► ObserverLayer（簇标签 / 孤立，只读）     │
       └─────────────────────────────────────────────┼──────────────────────────────────────────┘
                                                     ▼
                     EventBus（信号）──► Presentation（场景、可视化、推理板、简报、存档）
```

**硬性边界**：`scripts/core/`、`scripts/systems/`、`scripts/npc/` 不得 `preload` 任何 `scenes/`；模拟内核必须能在无渲染环境下跑完一局（批量标定与单测依赖这一点）。

## 2. 分层职责

| 层 | 目录 | 职责 | 禁止 |
|---|---|---|---|
| 模拟内核 | `scripts/core/` | 时间推进、矩阵与压力状态、结算 | 依赖节点树/UI |
| 规则层 | `scripts/systems/` | 人物行为的触发与效果、影响力传导（§10） | 角色名/ID 判断 |
| 观察层 | `scripts/systems/observer/` | 簇标签、孤立标签 | 回写任何数值 |
| 决策层 | `scripts/npc/` | NPC 的**规则选择**（用哪条规则、选谁） | 绕过规则直接改数值 |
| 表现层 | `scenes/`、`scripts/ui/`、`scripts/game/` | 渲染、输入、动画、推理板、简报界面 | 直接改矩阵（只能通过内核 API） |
| 全局单例 | `autoload/` | 状态持有、事件总线、存档、配置读取 | 承载玩法规则 |

### 2.1 行为执行组件（2026-10-07）

十种行为执行体位于 `scripts/systems/behaviors/`，每种行为是独立 `RefCounted` 组件；本局 `BehaviorRegistry` 固定注册并分发，`BehaviorContext` 提供状态读取、统一结算、占用、观测、RNG 和事件通知。上下文对内核与注册表采用弱引用，组件不持有矩阵副本或独立随机数。

`SimCore` 保留状态、时间、公式、决策与完成机制；原 `_do_*` 方法保留为兼容转发。搭话成功复用闲聊组件，执行/随机数/通知顺序保持原样。详细接口与验证见 [行为组件重构设计](../superpowers/specs/2026-10-07-behavior-components-design.md)。

### 2.2 统一闲聊与加入接线（2026-10-08 已实施）

[完整可玩流程计划](../superpowers/plans/2026-10-07-chat-playable-loop.md) 规定：闲聊是同一个行为，通用加入操作选择参与已有聊天，新请求统一为 kind=chat、mode=start/join，不再提供搭话菜单。实施落点：

| 模块 | 职责 |
|---|---|
| `scripts/core/activity_sessions.gd` | 真实共同活动（谁和谁此刻真在一起）：成员、参与连线、统一结束点；一人只在一场活动里 |
| `scripts/core/interaction_space.gd` | 纯几何：范围判定与「连线是否被桌椅挡住」；由场景一次注入，不引用任何节点 |
| `scripts/core/player_interactions.gd` | 只读预览、内核分配请求编号、原子提交、请求状态与完成／中断；弱引用内核 |
| `scripts/core/player_chat_intel.gd` | 玩家专属线索：条数由对象透明度决定、每条单轴、独立有种子随机流、历史日志 |
| `scripts/game/player_interaction_controller.gd` | 选择／接近／校验／提交／转笔／反馈状态机；消费移动与内核通知，不自己判定 |
| `scripts/game/activity_ring_presenter.gd` + `assets/shaders/activity_ring.gdshader` | 脚下圈：个人圈同色，真实会话用 SDF 并集融成一块连续区域（无内部双边框） |
| `scripts/ui/` 的四个组件 | 无字聊天气泡、四情绪（文字版，八图待收录）、唯一聊天操作菜单、转笔／进度／线索与历史列表 |

表现层只读结果：脚下圈与气泡只跟**真实会话**走，未揭晓的加入者在揭晓前不进融合区域；判定与结算一律在内核。新表 `data/rules/player_interaction.csv`、`data/ui/chat_feedback_style.csv` 承载几何与呈现参数，既有平衡数值未改动。旧 `join_chat` 组件／配置暂留兼容，只作 `chat`＋`mode=join` 的别名入口，不再向新 UI 暴露。

## 3. 目录约定

```
autoload/        全局单例（注册到 project.godot）
  ├─ game_state.gd        当前局状态与推进入口
  ├─ event_bus.gd         全局信号总线
  ├─ config.gd            配置表缓存与转发（解析在 scripts/core/config_loader.gd）
  └─ save.gd              存档（单日 = 一个存档单元）
data/            配置与数值（代码只读）
  ├─ characters/  角色种子表
  ├─ rules/       规则参数
  └─ balance/     W_event 与系数
scenes/
  ├─ ui/          菜单与界面（main_menu 等）
  ├─ game/        玩法场景（clue_board_1 线索板、classroom3D 教室）
  └─ components/  可复用组件
scripts/         与 scenes/ 同构：ui/ game/ core/ npc/ systems/
resources/       .tres 资源（主题、样式盒）
tests/           GUT / gdUnit4
tools/           离线脚本（批量标定、数据校验）
```

## 4. 关键数据流

1. `TimeSystem` 推进 tick，按当前相位（课间 / 上课 / 放学结算）决定启用哪些规则（主文档 §3.3）。
2. `RuleScheduler` 按规则优先级与触发条件收集本 tick 的候选交互。
3. 规则执行 → 通过 `Relations` 与 `Stress` 接口写入，统一走 主文档 §6.1 增量公式（传导类除外）。
4. 每 tick 末：`ObserverLayer` 只读输出标签；**涓流结算（传导 / 共同学习 / 独处恢复）每天 2 次**（`settle_interval`=240 tick，判据用全程 tick 计数）。
5. 事件经 `EventBus` 广播给表现层与日志；日志是简报（主文档 §14）与推理板的唯一数据源。
6. 每日结束执行跨天结算（主文档 §3.5）并生成《每日简报》。

## 5. 不可破坏的约束

- **禁止脚本化**：不得出现"第 N 天/第 N 段必然发生 X"的硬编码剧情。
- **禁止角色 ID 判断**：行为层只能是 `f(性格四维, 透明度, 状态)` 的纯函数（主文档 §11.1）。
- **观察层只读**：簇标签与孤立标签不回写矩阵。
- **数值集中**：增量、阈值、系数一律来自 `data/`，脚本中不得出现魔法数字。
- **可无头运行**：内核必须支持 `godot --headless` 跑完整局（标定与测试前提）。

## 场景导航（2026-10-07）

主菜单「新游戏」直接进入用户指定的 `scenes/game/classroom3D.tscn`，该 3D 场景挂接导航脚本与 CanvasLayer 上的暂停菜单；`Actors` 节点（`scripts/game/classroom_actors.gd`）按内核只读访问器 `seat_of(i)` 把本局每个节点摆到 `Seats/<seat_id>` 上，立绘查 `data/characters/appearance.csv`；每个人物再挂一个 `ActorWalker` 组件（`scenes/components/actor_walker.tscn`，只负责「怎么走」）。切场景前由 `main_menu.gd` 调 `GameState.start_game(seed, 难度)` 建本局唯一的内核实例。教室按 Esc 暂停；暂停菜单支持继续、设置和返回主菜单，返回时解除暂停。已有存档时沿用新游戏确认弹窗。菜单资源引用使用搬迁后的 `scripts/ui/`、`scenes/ui/` 和 `resources/` 路径。

课间走动由 `SimulationClock`（`scripts/game/simulation_clock.gd`）驱动真实相位：时钟把真实经过时间换算成整数 tick，只调用内核的 `advance_tick()` 与 `finish_time_boundary()`；课间 / 上课边界经 `phase_changed` 通知 `classroom_roam.gd`，后者按 §10.4 的权重式在站立点（`StandPoints/*` 公共点 + `Seats/*` 座位点）之间加权抽目标，进上课全体归位。移动耗时 = `behaviors.csv` 的 `move.duration` × `time_presentation.csv` 的每 tick 真实秒数，数值全部来自 `data/`。**内核侧走动（`position` / `do_move`）仍未落地**，接上后由 `position_of(i)` 取代表现层的位置推断。

时间显示由 `scenes/ui/time_hud.tscn`（`scripts/ui/time_hud.gd`）承担，只读时钟快照（阶段名来自 `time_presentation.csv`）；日末停在简报，第 30 天结束后停止模拟。**仍需实现**：日报内容组件、完整存档恢复（当前只有时间侧字段可恢复）。

### 教室导航与「两套几何」的分工（2026-10-07）

教室里同时存在两种几何口径，**职责正交、不重叠**，不要合并：

| 用途 | 口径 | 来源 |
| --- | --- | --- |
| **NPC 走动的路线** | **导航网格** | `classroom3D.tscn` 的 `Navigation`（`NavigationRegion3D`）+ `NavGeometry`、`desk_chair.tscn` 的 `NavBlocker`（都在 `nav_geometry` 组），烘焙产物 `resources/navigation/classroom_nav.tres` |
| **玩家路线（点击寻路 / 接近算路）** | 矩形网格 A\* | `PlayerController._build_nav()`，桌椅矩形从 `Seats/*/Desk` 派生 |
| **内核的空间判定（范围 / 连线阻挡）** | 矩形 + 房间边界 | 场景经 `PlayerController.interaction_geometry()` 一次注入 `InteractionSpace` |

**为什么不让导航网格当唯一事实源**：`scripts/core/` 不得引用表现层节点（`interaction_space.gd` 文件头即写明「不引用 Node3D / 导航节点」），内核要的是**纯数据**；要让内核按导航判可达，得先烘焙一份纯数据快照再注入，属独立工程。

**烘焙是流程的一部分**：改了 `Seats/*` 的占位几何或 `NavGeometry` 之后必须重烘

```bash
godot --headless --path . --script tools/bake_classroom_nav.gd          # 生成/更新烘焙产物
godot --headless --path . --script tests/integration/check_classroom_nav.gd   # 连通性验收
```

`tests/unit/test_nav_config.gd` 会先抓到「data 与烘焙产物不一致」；`check_classroom_nav.gd` 查的是**连通性**（公共起点到每个目标真的有路径），不是「离导航面近不近」——后者证明了覆盖、却证明不了可达。

**座位站位**：`desk_chair.tscn` 的 `StandSpot`（`z = -0.80`，行间过道中心）是落位 / 站位 / 玩家目标的唯一来源；`SitPoint`（`z = -0.45`，椅子处）是**坐姿显示锚点**，留给坐下帧动画，不参与行走。

## 6. 待细化

### 聊天空间与移动互斥（2026-10-08）

`ClassroomRoam` 在初始化时注入每个角色的座位入口纯坐标，通过 Walker 的开始/结束信号立即同步 `set_moving`，到达时先写最终位置再解除移动状态。NPC 选目标与聊天执行体均使用 `SimCore.chat_pair_in_range`；玩家预览/提交也使用同一判定（前后座位例外见主文档 §10.5）。行为占用、真实会话和睡眠阻止离座；移动状态阻止发起/接受聊天。真实场景的时间边界先清理聊天，再通知归位。活动圈继续只读真实会话，不用隐藏错误圈来代替规则修复。

`tests/unit/test_social_movement.gd` 覆盖远距、移动互斥和座位例外；`tests/integration/test_social_movement_scene.gd` 在真实教室推进整段课间，同时要求发生聊天与走动，检查聊天成员静止和距离约束。Python/GDScript 无场景几何的离线对拍保持抽象基线；六道门不替代此场景验收。
